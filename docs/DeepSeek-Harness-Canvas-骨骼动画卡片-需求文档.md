# 骨骼动画卡片 · 需求文档

**版本**：v2.0（方案评审稿，未动代码；v2.0 推翻 v1.0 的「自研 P1 扩展」路线，编辑器改用 Rigby2D 实现）
**日期**：2026-11-11
**参考产品**：[LoongBones 龙骨动画](https://www.loongbones.com/)（功能对照）；[Rigby2D](https://github.com/jaisurya-dev-art/rigby2d)（**编辑器实现本体**，MIT / Apache-2.0，v0.5.1）
**现状**：仓内已有 skeleton2d-lite 卡（正弦无缝循环、自动分层、网格蒙皮、四模式自研编辑器、DragonBones 导出）。本版回答：**编辑器整只换成 Rigby2D，它的功能我们怎么复用、数据怎么接、自研代码退到哪里**。
**配套技术方案**：[`DeepSeek-Harness-Canvas-骨骼动画卡片-技术文档.md`](./DeepSeek-Harness-Canvas-骨骼动画卡片-技术文档.md)（v2.0 集成架构）

## 〇、一句话结论

骨骼动画卡的**全屏编辑器不再自研**：把 Rigby2D 的 web 编辑器 vendor 进本仓（MIT/Apache 双许可允许），裁掉桌面壳与重型可选项后静态嵌入宿主，以 iframe 挂进现有全屏预览器的「编辑」档，文件读写经一层桥接走我们的工作区。**它的全部编辑能力直接成为卡片的能力**——自动网格、贝塞尔曲线编辑器、IK/变换/路径/物理约束、洋葱皮、姿势库、AutoRig、PSD 分层导入、图集与雪碧图导出，v1.0 里 P1/P2 自研清单整体作废。自研部分收缩为三件：**生成侧**（会话一句话 → 初始 rig，继续用 `layerize.ts` 的确定性分层）、**卡面轻播放**（卡面呼吸动画不能拖重型编辑器）、**桥接与保存链**（iframe 双向桥 + 工作区写盘纪律）。

## 一、为什么改道（v1.0 → v2.0）

| | v1.0（自研扩展，已废弃） | v2.0（Rigby2D 集成，本版） | 原因 |
|------|------|------|------|
| 编辑器 | 四模式自研编辑器继续加功能 | Rigby2D 编辑器 vendor 进来 | 它的编辑器成熟度是「专业动画软件」级：graph editor、dopesheet、姿势库、重定向、多语言（含简中）、可缩放面板——自研追平要按月计 |
| P1 自研四件（自动网格/贝塞尔/IK/洋葱皮） | 全部自己写 | **全部免费**——Rigby2D 全有 | v1.0 的每一项都是重复造轮子 |
| P2 五项（约束/物理/图集/多图分层/变换约束） | 二期自研 | 也基本免费（约束/物理/图集/PSD 导入全有） | 同上 |
| 生成侧（一句话生成） | 升级提示词预设 | 保留，落点改成 Rigby2D 格式 | 生成是**我们独有的架构优势**（卡片在会话引擎里，Rigby2D 只有外挂 MCP），不做也是白不做 |
| 卡面播放 | skeleton2d-stage 继续用 | 引 Rigby2D 的 **JS runtime** 播放 | 卡面要轻、编辑器要全——两个面分开伺候 |
| 产物格式 | `.skeleton2d.json` v2 | v3 = 壳 + 内嵌 Rigby2D 项目 | 见技术文档 §四（文件即产物不破，kind 检测不变） |

**不变的**：文件即产物、卡片即会话、kind 由文件证据认定、引用即数据、全屏预览器的 chrome 与协商机制、导出与发布框架。

## 二、复用清单（Rigby2D 提供什么）

全部进卡片的编辑能力（对照其 README，逐项确认复用）：

- **装配**：骨骼、加权网格、linked meshes、贴图序列、skins、events、clipping、paths；**IK / 变换 / 路径 / 物理 / 滑杆五类约束**。
- **动画**：Setup/Animate 双模式、dopesheet、**带贝塞尔手柄的 graph editor**、洋葱皮、姿势库、面部控制、角色重定向。
- **AutoRig**：分层 PSD/SVG 一步出 rig（骨骼 + 关节 + 弯曲网格 + IK）。
- **导入**：PSD（ag-psd）、**DragonBones 项目**（我们旧导出的存量素材可以直接搬进来）、Spine 导出。
- **导出**：无损骨架 JSON / `.skel`、纹理图集、雪碧图（循环处接合）、PNG 序列、WebM（带 alpha）/ MP4。
- **工程化**：简体中文界面、自动保存与备份、可缩放面板、快捷键参考。

## 三、功能需求（集成视角）

**RI1 vendor fork 与构建集成**
把 Rigby2D 以 subtree/vendor 目录进本仓（记上游 commit、license 声明随附）。构建裁剪：剥掉 Tauri 壳、pyodide（Python 插件沙箱）、@huggingface/transformers（口型同步 Whisper）——这三样是桌面/重 AI 依赖，浏览器嵌入用不上且体积不可接受。出口判据：`node build.mjs` 一条命令产出含编辑器静态包的完整 lib；编辑器包独立目录、懒加载（打开编辑模式才拉）。

**RI2 编辑器嵌入与双向桥**
全屏预览器「预览/编辑」开关的**编辑档**换成 Rigby2D：iframe 挂载静态包，fork 内加一个桥模块（`bridge`）：打开（工作区读产物 + 贴图经工作区路由喂给它）、保存（它的保存事件 → `writeText` 落盘产物，沿用防抖 + 卸载冲刷 + 回读 adopt 四步纪律）、贴图（`markdownImageSrc` 同款路由）。出口判据：编辑器里改一处，落盘后重开所见一致（保存链全走通）；卡面与编辑器看到的动画一致。

**RI3 产物格式 v3**
`.skeleton2d.json` 升 v3：外壳字段（format/version/贴图引用）+ `rigby` 段内嵌其原生项目数据。kind 检测、分目录、引用关系全部不变。旧 v1/v2 模型在编辑器打开时一次性迁移（v2 的参数化动作烘成关键帧——**迁移是有损的，判据要求迁移前弹提示**）。

**RI4 卡面轻播放**
卡面引入 Rigby2D 的 **JS runtime**（MIT，独立小包）播放 v3 产物；旧格式继续走现有 `skeleton2d-stage`，迁移后退役。出口判据：卡面 30fps 不掉帧；一张卡的开销不随编辑器包体积涨（runtime 与编辑器是两份独立产物）。

**RI5 生成侧保留**
`canvas_generate_skeleton2d` 工具与 `layerize.ts` 分层保留，落点改为 v3 产物（vendored core 里的 autorig 能力做初始绑骨，我们的确定性分层做贴图预切）。出口判据：一句话生成 → 打开编辑器直接可调（不用先手动装配）。

**RI6 引用与引用即数据**
贴图仍是普通图片文件（相对路径引用），v3 外壳字段负责指路；Rigby2D 内部的图集引用由桥在打开/保存时映射回工作区路径。

## 四、明确不做的事

1. **桌面壳 / 自动更新 / 偏好里的桌面特性**：宿主是插件，不带入 Tauri。
2. **Python 插件沙箱（pyodide）与口型同步（本地 Whisper）**：体积与收益不成比例；口型若将来有需求，走会话侧音频工具而不是编辑器内嵌 ML。
3. **它的影视工作区 / 场景合成 / 多角色舞台**：单卡单骨架边界不变。
4. **Spine `.skel` 二进制导出**：格式层面能导但许可风险自担——不开启该出口，JSON 路线够用。
5. **实时物理进卡面播放**：卡面只播数据，物理结果以关键帧形式存在（编辑器里烘）。
6. **直接改 Rigby2D 上游核心逻辑**：fork 差异收敛在桥与配置层（升级策略见技术文档 §八）；改核心 = 永远追不动上游。

## 五、非功能需求

- **许可合规**：MIT OR Apache-2.0 按原文件随附声明；Rigby2D 商标不用于我们的界面宣称（界面上标注「编辑器基于 Rigby2D (MIT)」）；THIRD_PARTY 清单登记。
- **体积红线**：编辑器静态包**懒加载**，不得进首屏 bundle；裁剪后包体积记录进判据（目标 < 8MB，含 WASM 的话另行评审）。
- **卡面性能**：30fps；runtime 只认 v3 数据。
- **离线可用**：编辑器静态包本地分发，不依赖 rigby2d.com 任何在线资源。
- **保存纪律**：半写不留（writeText 原子性）+ 回读 adopt，老教训直接继承。
